# Как устроен поиск по каталогу: простое описание

Документ для разработчиков и администраторов: **какие таблицы**, **как строится индекс** и **как обрабатывается запрос**. Технические термины вынесены в [глоссарий](#глоссарий).

Подробнее в сжатом виде см. [catalog_search.md](catalog_search.md); код — [`CatalogSearchIndexService`](../lib/Service/CatalogSearchIndexService.php), [`MysqlLexemeTrigramSearchBackend`](../lib/Service/MysqlLexemeTrigramSearchBackend.php).

---

## Два режима (движка)

В настройках модуля задаётся **движок поиска** (`catalog_search_backend`):

| Движок | Суть |
|--------|------|
| **`mysql_lexeme_trigram`** (основной) | Словарь слов + триграммы, можно искать **подстроку внутри слова** («грамм» внутри «триграмм»). |
| **`legacy_token`** | Старый вариант: токены привязаны к товару целиком, в основном **начало слова** + при отсутствии результатов **fuzzy** (похожие слова). |

Дальше по тексту, если не сказано иначе, речь о **`mysql_lexeme_trigram`**.

## Какие таблицы задействованы

| Таблица | Зачем |
|---------|--------|
| **`myapp_catalog_search_meta`** | Одна строка настроек: версия индекса, хеш конфигурации, счётчики, дата полной синхронизации. По ней понимают, **готов** ли поиск и **совпадает ли** конфиг с тем, под который собирали индекс. |
| **`myapp_catalog_search_document`** | Один ряд на **родительский товар**: нормализованное имя, «тело» для справки, сортировка, активность. Нужен, чтобы отфильтровать неактивные и дать **бонус за совпадение в названии**. |
| **`myapp_catalog_search_lexeme`** | **Словарь**: каждая уникальная нормализованная строка-слово (лексема) один раз, с `ID`. |
| **`myapp_catalog_search_lexeme_trigram`** | У лексемы длины ≥ 3 символов — все **триграммы** (3 подряд символа UTF-8). По ним быстро находят кандидатов по **фрагменту** слова. |
| **`myapp_catalog_search_product_lexeme`** | Связь **товар ↔ лексема** + **вес** (насколько важно совпадение: имя, анонс, свойство и т.д.). |
| **`myapp_catalog_search_token`** | Только для **`legacy_token`**: старые пары товар + текстовый токен. |
| **`myapp_catalog_search_queue`** | Очередь товаров на **переиндексацию** после изменений. |
| **`myapp_catalog_search_job`** | Фоновые **полные** пересборки (job’ы в админке). |

Таблицы создаются автоматически при загрузке модуля ([`CatalogSearchIndexSchema`](../lib/Install/CatalogSearchIndexSchema.php)).

## Глоссарий

- **Нормализация текста** — приведение к единому виду: без HTML, в нижнем регистре, «ё»→«е», лишняя пунктуация убрана, пробелы ровные. Так «Товар» и «товар» становятся одним и тем же для индекса и запроса.

- **Токен (в запросе)** — отдельное «слово» из пользовательской фразы после нормализации и **разбиения по пробелам**, с выбрасыванием **стоп-слов** (например «и», «в»). В многословном запросе между токенами действует логика **AND**: товар должен подойти **по каждому** токену.

- **Лексема** — нормализованный **отрывок текста**, который кладём в словарь и связываем с товаром. Обычно это то же, что **слово** из описания (буквы/цифры подряд). В индекс не попадают «пустые» или небезопасные для SQL строки.

- **Дедуп (дедупликация)** — если одно и то же слово встретилось в **нескольких полях** товара, в индекс идёт **одна связь** с **максимальным весом** среди источников (не суммируем десять раз одно и то же слово).

- **Триграмма** — три символа подряд внутри строки (UTF-8).  
  Пример: из слова «триграмм» получаются «три», «риг», «игр», …  
  По триграммам ищут **где может жить подстрока**, не перебирая все товары подряд.

- **Словарь (лексем)** — таблица **уникальных** лексем. Триграммы хранят **на лексеме**, а не копируются на каждый товар: экономия места и единая логика.

- **Инверсный индекс** — структура «по ключу (триграмма / лексема) → список кандидатов», а не «товар → весь текст». Так быстрее искать по отдельным кускам.

- **Rare-first («сначала редкое»)** — среди триграмм **словова из запроса** сначала берут ту, у которой **меньше всего** записей в таблице триграмм (она сильнее **сужает** круг кандидатов).

- **Подтверждение (LOCATE)** — после отбора кандидатов по триграммам проверяем, что **подстрока запроса** реально входит в текст **лексемы** в словаре (а не случайное пересечение триграмм).

- **Вес (WEIGHT)** — целое число важности: совпадение в **названии** весит выше, чем в **детальном тексте**. При ранжировании по токенам берётся **максимальный** вес среди подходящих лексем товара.

- **Порог по сумме весов** — слишком слабые совпадения отсекаются; порог зависит от **числа слов в запросе** (см. код в бэкенде).

- **Бонус за имя** — если токен запроса **в начале названия** или **после пробела в названии**, к счёту добавляется фиксированный бонус (релевантность «в заголовке»).

- **Полная переиндексация** — job перечитывает весь каталог и пересобирает индекс с нуля.

- **Инкрементальная переиндексация** — только изменённые товары попадают в **очередь**, воркер вызывает `rebuildProduct` по одному `PRODUCT_ID`.

## Как строится поисковый индекс (пошагово)

### Когда запускается

- **Полная** пересборка: задание в админке (вкладка поиска) или CLI-воркер.
- **По одному товару**: событие инвалидации каталога → очередь → `CatalogSearchIndexService::rebuildProduct`.
- **Удаление товара**: из индекса убираются связи и документ (`removeProduct`).

### Этапы для одного активного товара (`rebuildProduct`)

1. **Снять старый индекс товара**  
   Удаляются строки в `myapp_catalog_search_product_lexeme` для этого `PRODUCT_ID` и запись в `myapp_catalog_search_document` (через бэкенд).

2. **Прочитать данные из Bitrix**  
   Название, при необходимости PREVIEW/DETAIL, значения **выбранных для поиска** свойств родителя, тексты с **торговых предложений** (по настройкам).

3. **Нормализация и извлечение «слов»**  
   Из каждого фрагмента текста получаются лексемы (последовательности букв/цифр). Для длинных слов может добавляться **укороченная «основа»** (heuristic stem в коде) — отдельный токен с меньшим весом.

4. **Сбор карты «лексема → вес»**  
   Одна и та же лексема из разных полей **не дублируется**: сохраняется **больший** вес ([дедуп](#глоссарий)).

5. **Запись документа**  
   В `myapp_catalog_search_document` — нормализованное имя, объединённое тело, сорт, активность.

6. **Запись в словарь и связей (бэкенд `indexProductLexemes`)**  
   - Для каждой лексемы: если такой строки ещё нет в `myapp_catalog_search_lexeme` — **INSERT**, и для длины ≥ 3 — посчитать и вставить **триграммы** в `myapp_catalog_search_lexeme_trigram`.  
   - Если лексема уже была в словаре — **новые триграммы не дублируются** (они уже привязаны к этой лексеме).  
   - В `myapp_catalog_search_product_lexeme` — связь `PRODUCT_ID`, `LEXEME_ID`, вес (при конфликте ключей — **GREATEST** веса).

7. **Мета и готовность**  
   При полном job обновляются счётчики, хеш конфигурации, флаг готовности (см. `finalizeFullBuild`).

### После полной пересборки

Ожидается, что в meta **`CONFIG_HASH` = `searchConfigHash()`** и **`catalog_search_index_ready=Y`**, иначе поиск может быть отключён до совпадения.

## Как работает поиск по запросу (`mysql_lexeme_trigram`)

Ниже — **логическая** цепочка; конкретный SQL может меняться, смысл остаётся.

### Шаг 0. Проверки (`CatalogSearchService`)

- Индекс **готов** и конфиг не «протух».
- Запрос после нормализации не короче 2 символов.

### Шаг 1. Кеш числа результатов (опционально)

Для **пагинации**: если открыта не первая страница и в кеше уже есть **total** для этой нормализованной фразы, тяжёлый **`COUNT(*)`** в БД может **не выполняться** — подставляется сохранённое число. Кеш привязан к версии данных поиска (эпоха меняется при изменении индекса).

### Шаг 2. Разбор запроса

- Нормализация той же схемой, что при индексации.
- **Токены** — слова запроса без стоп-слов.
- Между токенами — **AND**: каждый токен должен «найтись» у товара.

### Шаг 3. Для каждого токена — найти подходящие лексемы в словаре

**Если токен длиной ≥ 3 символов**

1. Строятся **триграммы** токена.
2. Считается частота каждой триграммы в таблице (сколько лексем её содержат) — для стратегии **rare-first**.
3. Берётся «самая редкая» триграмма → список `LEXEME_ID`.
4. С остальными триграммами этого же токена делается **пересечение** списков лексем (кандидаты всё уже в словаре).
5. **Подтверждение**: для кандидатов проверяется, что **подстрока токена** есть в `LEXEME_TEXT` (функция уровня `LOCATE`), **только по словарю**, не по всей таблице товаров.

**Если токен короче 3 символов**

Триграмм мало или нет — ищем по **точному совпадению** или **префиксу** в `myapp_catalog_search_lexeme` (отдельный путь без полного триграммного индекса для такой короткой лексемы).

Если по любому токену лексем не найдено — ответ **пустой**.

### Шаг 4. Пересечение по токенам на уровне товаров

Нужны товары, у которых для **каждого** токена запроса есть хотя бы одна подошедшая лексема. В реализации это выражается **SQL-подзапросами** по `myapp_catalog_search_product_lexeme` и активному документу.

### Шаг 5. Счёт релевантности и отсечение

- Для каждого токена берётся **максимальный вес** связи товар–лексема среди подошедших лексем.
- Сумма по токенам + **бонус за имя**, если токен «сидит» в нормализованном названии.
- Отбрасываются товары ниже **порога** по сумме.

### Шаг 6. Сортировка и страница

- Сортировка по убыванию счёта, затем по `PRODUCT_ID`.
- Выбирается **ровно одна страница** (`LIMIT`/`OFFSET` в БД).

### Шаг 7. Общее число совпадений (`total`)

Отдельный запрос **`COUNT(*)`** по тому же фильтру (дорого на «частых» словах). Может быть пропущен при пагинации, если сработал кеш (см. шаг 1).

### Шаг 8. Карточки товаров

По списку `PRODUCT_ID` страницы подгружаются данные для отображения (имя, цена, картинка) — уже **обычные** запросы каталога, не поисковый индекс.

## Кратко про `legacy_token`

- Индекс: `myapp_catalog_search_token` + документ.
- Поиск: совпадение **целого токена** или **начала** (`TOKEN = …` / `LIKE 'q%'`).
- Если строгий поиск пуст и есть длинные токены — фаза **fuzzy** (расстояние редактирования).
- Подстрока **внутри** длинного слова как в лексемном движке **не цель** этого режима.

---

## Связь с фильтром каталога

**Индекс поиска** и **индекс фильтра** (разделы, свойства, цены в `filter_*` таблицах) — **разные** системы. Изменение «свойств в фильтре» в опциях влияет на **фильтр**, а поисковый индекс пересобирается по **своим** настройкам (`catalog_search_product_property_codes` и т.д.), если меняете их — смотрите [catalog_search.md](catalog_search.md) и `searchConfigHash()`.
