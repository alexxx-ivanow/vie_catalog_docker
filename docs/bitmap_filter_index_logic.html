Bitmap Index фильтра каталога: подробное описание

Побитовый индекс для быстрой выборки ID товаров в GET /vue_catalog/api/v1/catalog/goods. Публичный API и Vue-фронт не меняются — меняется только внутренний движок listing при catalog_filter_engine=bitmap.

Краткая справка в репозитории: bitmap_filter_index.md. См. также денормализованный индекс (product_filter_index.md) и снапшоты UI-фильтра (/catalog/filters).

Два слоя: listing и блок фильтра

СлойЗадачаAPI
Product filter index (bitmap / denormalized / legacy) Список товаров: section + свойства + цена → total + страница ID CatalogService::getGoods()
Filter snapshots (aggregate) Чекбоксы, min/max цены в боковом фильтре CatalogService::getFilters() → myapp_catalog_filter_aggregate

Bitmap не подменяет снапшоты: после смены движка listing всё равно нужны актуальные снапшоты для UI фильтра (отдельная пересборка aggregate).

Три движка listing

На вкладке «Индекс фильтрации» — одна опция catalog_filter_engine (активен ровно один):

ЗначениеПоведение
legacy Прямые SQL по b_iblock_*, свойствам, ценам Bitrix.
denormalized Таблицы myapp_catalog_filter_*, ProductFilterQueryService (JOIN по filter_value).
bitmap Таблицы myapp_catalog_bitmap_*, BitmapFilterService (побитовые маски + лёгкий SQL по bitmap_products).

Фабрика: CatalogFilterEngineFactory. Совместимость: пустой catalog_filter_engine + старый use_product_filter_index=Y → denormalized.

Инвалидация: очередь / remove при изменении товара выполняется только для активного движка (либо пока идёт job построения этого индекса). Неактивный bitmap не обновляется при правках каталога.

Особый случай: при активном bitmap параметр ?article= ведёт к fallback на legacy — артикул в bitmap не индексируется.

Когда bitmap используется

В BitmapIndexService:

  • shouldUseIndex() = движок bitmap и индекс готов.
  • Готовность: опция bitmap_index_ready=Y и meta.CONFIG_HASH === indexConfigHash().
  • indexConfigHash() завязан на iblock, коды свойств фильтра, тип цены, SKU/offers — смена без пересборки → индекс «не готов» / stale в админке.

Ключ кеша getGoods учитывает версию bitmap-индекса — после full build кеш списков сбрасывается по версии.

Таблицы и смысл полей

ТаблицаНазначение
myapp_catalog_bitmap_products Один ряд на товар: PRODUCT_ID, BITMAP_POSITION (индекс бита), ACTIVE, SORT, PRICE (мин. цена выбранного типа, как в denormalized).
myapp_catalog_bitmap_index Ключ PROPERTY_ID + VALUE_ID → бинарная маска (MEDIUMBLOB): бит N = «товар на позиции N имеет это значение».
myapp_catalog_bitmap_value_dict Словарь VALUE_ID для строковых и числовых значений свойств.
myapp_catalog_bitmap_membership Текущий набор ключей (property, value) у товара — для инкрементального снятия битов при rebuildProduct.
myapp_catalog_bitmap_status Версия, hash конфига, счётчики, статус, MAX_POSITION, длина битового поля.
myapp_catalog_bitmap_queue / _job Очередь ID на переиндексацию и фоновые полные пересборки (админка / агент).

Разделы в масках

PROPERTY_ID = 0 — не ID свойства инфоблока, а sentinel BitmapStorage::SECTION_PROPERTY_ID; VALUE_ID = SECTION_ID. Обычные свойства фильтра имеют PROPERTY_ID > 0 (например MATERIAL = 11).

Глоссарий

  • BITMAP_POSITION — целое 0…N; у каждого проиндексированного товара своя позиция; это индекс бита во всех масках.
  • Маска (mask) — бинарная строка длины bit_length; бит на позиции P включён, если товар с BITMAP_POSITION=P попадает под ключ (section или значение свойства).
  • OR внутри свойства — выбрано несколько значений одного свойства → объединение масок значений.
  • AND между свойствами — пересечение масок разных свойств.
  • popcount — число единичных битов в итоговой маске после фильтра (кандидаты до цены в SQL).
  • index path — getGoods не ходит в legacy SQL по свойствам; bitmap_path: true в _perf.

Построение и инкремент

Полная пересборка

  • Вкладка «Bitmap Index» → «Полное построение» (AJAX-шаги).
  • CLI: php local/modules/myapp.catalog/tools/bitmap_index_worker.php --batch=20.
  • Job наполняет очередь порциями; BitmapIndexService::rebuildProduct на каждый ID.

Один товар (rebuildProduct)

  1. Транзакция; прочитать старую позицию и membership.
  2. Если товар неактивен — снять биты, пометить строку в bitmap_products неактивной.
  3. Иначе: выделить/сохранить BITMAP_POSITION, clearBits по старым ключам.
  4. Собрать новые ключи (разделы + значения свойств фильтра); для каждого setProductBit в соответствующую маску.
  5. Обновить bitmap_products (PRICE через ту же логику, что у denormalized).
  6. Увеличить soft version индекса.

Шаг в админке

Поле «Товаров за один HTTP‑запрос» — от 1 до 120 (как на вкладке «Индекс фильтрации»). Агент/cron использует отдельную опцию bitmap_index_batch_size (потолок 100).

Как обрабатывается запрос фильтра

Точка входа: BitmapFilterService::queryProductIds ← CatalogService::getGoods.

  1. Поддерево раздела — список SECTION_ID (perf: bitmap_section_ids).
  2. Маска раздела — OR масок всех разделов поддерева (perf: bitmap_section_or).
  3. Маски свойств — для каждого выбранного свойства OR по значениям, затем AND между свойствами (perf: bitmap_props_and_or).
  4. Пересечение — AND маски раздела и маски свойств (если заданы).
  5. Итерация битов — список BITMAP_POSITION кандидатов (perf: bitmap_iterate_bits, meta.bitmap_popcount).
  6. Total — кеш CACHE_DIR_GOODS_COUNT или SQL count по bitmap_products с фильтром цены (perf: bitmap_goods_count).
  7. Страница — SQL list с ORDER BY (sort/name/price) + LIMIT (perf: bitmap_goods_list).
  8. Карточки — goods_list_details по 12 ID (как у других движков).

Логика свойств:

  • типы: enum (L), string (S) — точное совпадение, number (N) — точное;
  • multiple — бит выставляется в маске каждого значения;
  • цена price_from / price_to и сортировка по цене — по колонке p.PRICE в bitmap_products, без join к b_catalog_price на этапе фильтра.

Сопоставление позиций и SQL

После масок в PHP остаётся ограничить SQL по списку позиций (или сканировать всех активных, если маски фильтра не задавали сужение).

bitmap_popcountmeta.bitmap_id_resolveПоведение
≤ 512 position_in BITMAP_POSITION IN (...) в WHERE.
> 512 position_temp CREATE TEMPORARY TABLE (MEMORY), пакетный INSERT позиций, INNER JOIN в count и list; perf: bitmap_positions_temp.
без сужающей маски full_scan_active Все активные товары в bitmap_products (редко на реальном фильтре).

Порог в коде: POSITION_IN_THRESHOLD = 512 (BitmapFilterService). Цель — не слать в MySQL два запроса с тысячами литералов в IN.

Замеры (_perf) и сравнение с denormalized

Как у других движков:

GET /vue_catalog/api/v1/catalog/goods?section=33&...&perf=1&skip_cache=1

В ответе:

  • meta.filter_engine=bitmap, meta.count_mode=bitmap_index, bitmap_path=true;
  • index_query_ms — время индексной части;
  • stages_ms.list — в основном сборка карточек, не второй тяжёлый SQL listing.

Типичный сложный фильтр (несколько свойств + цена): denormalized часто упирается в index_goods_count (~секунда COUNT(DISTINCT) с JOIN); bitmap — ~десятки ms на маски + умеренный SQL по bitmap_products. Итоговое время страницы всё равно включает ~150–200 ms на карточки.

CLI:

  • tools/compare_filter_query.php --section=ID --engine=bitmap — сравнение ID с legacy/denormalized;
  • tools/bench_filter_engines.php --section=ID — бенч трёх движков.

Админка и операции

  • Вкладка «Bitmap Index» — статистика, batch, полное построение, остановка, очистка.
  • Проверить / repair — BitmapIndexValidator.
  • Переключение движка — только на «Индекс фильтрации»; на вкладке Bitmap показывается активный движок.

Нужно ли переиндексировать

После правок только чтения/запросов (temp table вместо IN, лимиты batch в админке, CSS) — полная пересборка не нужна: маски и bitmap_products не меняются.

Пересборка нужна, если:

  • изменился indexConfigHash() (свойства фильтра, iblock, цена, SKU);
  • индекс не готов / stale в админке;
  • была очистка или repair с пересборкой;
  • validator показал расхождения.

Roaring (будущее)

Сжатие Roaring не подключено. Сейчас — plain binary в MEDIUMBLOB. Переоценка — по blob_bytes и памяти на 100k+ товаров после bench_filter_engines.php.
