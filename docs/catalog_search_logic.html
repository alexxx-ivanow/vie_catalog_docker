Два режима (движка)

В настройках модуля задаётся движок поиска (catalog_search_backend):

ДвижокСуть
mysql_lexeme_trigram (основной) Словарь слов + триграммы, можно искать подстроку внутри слова («грамм» внутри «триграмм»).
legacy_token Старый вариант: токены привязаны к товару целиком, в основном начало слова + при отсутствии результатов fuzzy (похожие слова).

Дальше по тексту, если не сказано иначе, речь о mysql_lexeme_trigram.

Какие таблицы задействованы

ТаблицаЗачем
myapp_catalog_search_meta Одна строка настроек: версия индекса, хеш конфигурации, счётчики, дата полной синхронизации. По ней понимают, готов ли поиск и совпадает ли конфиг с тем, под который собирали индекс.
myapp_catalog_search_document Один ряд на родительский товар: нормализованное имя, «тело» для справки, сортировка, активность. Нужен, чтобы отфильтровать неактивные и дать бонус за совпадение в названии.
myapp_catalog_search_lexeme Словарь: каждая уникальная нормализованная строка-слово (лексема) один раз, с ID.
myapp_catalog_search_lexeme_trigram У лексемы длины ≥ 3 символов — все триграммы (3 подряд символа UTF-8). По ним быстро находят кандидатов по фрагменту слова.
myapp_catalog_search_product_lexeme Связь товар ↔ лексема + вес (насколько важно совпадение: имя, анонс, свойство и т.д.).
myapp_catalog_search_token Только для legacy_token: старые пары товар + текстовый токен.
myapp_catalog_search_queue Очередь товаров на переиндексацию после изменений.
myapp_catalog_search_job Фоновые полные пересборки (job’ы в админке).

Таблицы создаются автоматически при загрузке модуля (CatalogSearchIndexSchema).

Глоссарий

  • Нормализация текста — приведение к единому виду: без HTML, в нижнем регистре, «ё»→«е», лишняя пунктуация убрана, пробелы ровные. Так «Товар» и «товар» становятся одним и тем же для индекса и запроса.
  • Токен (в запросе) — отдельное «слово» из пользовательской фразы после нормализации и разбиения по пробелам, с выбрасыванием стоп-слов (например «и», «в»). В многословном запросе между токенами действует логика AND: товар должен подойти по каждому токену.
  • Лексема — нормализованный отрывок текста, который кладём в словарь и связываем с товаром. Обычно это то же, что слово из описания (буквы/цифры подряд).
  • Дедуп (дедупликация) — если одно и то же слово встретилось в нескольких полях товара, в индекс идёт одна связь с максимальным весом среди источников.
  • Триграмма — три символа подряд внутри строки (UTF-8). Пример: из слова «триграмм» получаются «три», «риг», «игр», … По триграммам ищут где может жить подстрока, не перебирая все товары подряд.
  • Словарь (лексем) — таблица уникальных лексем. Триграммы хранят на лексеме, а не копируются на каждый товар.
  • Инверсный индекс — структура «по ключу (триграмма / лексема) → список кандидатов», а не «товар → весь текст».
  • Rare-first («сначала редкое») — среди триграмм слова из запроса сначала берут ту, у которой меньше всего записей в таблице триграмм.
  • Подтверждение (LOCATE) — после отбора кандидатов по триграммам проверяют, что подстрока запроса реально входит в текст лексемы в словаре.
  • Вес (WEIGHT) — целое число важности: совпадение в названии весит выше, чем в детальном тексте. По токенам берётся максимальный вес среди подходящих лексем товара.
  • Порог по сумме весов — слишком слабые совпадения отсекаются; порог зависит от числа слов в запросе.
  • Бонус за имя — если токен запроса в начале названия или после пробела в названии, к счёту добавляется фиксированный бонус.
  • Полная переиндексация — job перечитывает весь каталог и пересобирает индекс с нуля.
  • Инкрементальная переиндексация — только изменённые товары попадают в очередь, воркер вызывает rebuildProduct по одному PRODUCT_ID.

Как строится поисковый индекс (пошагово)

Когда запускается

  • Полная пересборка: задание в админке (вкладка поиска) или CLI-воркер.
  • По одному товару: событие инвалидации каталога → очередь → CatalogSearchIndexService::rebuildProduct.
  • Удаление товара: из индекса убираются связи и документ (removeProduct).

Этапы для одного активного товара (rebuildProduct)

  1. Снять старый индекс товара — удаляются строки в myapp_catalog_search_product_lexeme для этого PRODUCT_ID и запись в myapp_catalog_search_document (через бэкенд).
  2. Прочитать данные из Bitrix — название, при необходимости PREVIEW/DETAIL, значения свойств родителя, тексты с торговых предложений (по настройкам).
  3. Нормализация и извлечение «слов» — лексемы из фрагментов; для длинных слов может добавляться укороченная «основа» с меньшим весом.
  4. Сбор карты «лексема → вес» — одна лексема из разных полей не дублируется: сохраняется больший вес.
  5. Запись документа в myapp_catalog_search_document.
  6. Запись в словарь и связей (indexProductLexemes): новая лексема → INSERT в словарь и триграммы (длина ≥ 3); связь товар–лексема–вес в myapp_catalog_search_product_lexeme.
  7. Мета и готовность — при полном job обновляются счётчики, хеш конфигурации, флаг готовности (finalizeFullBuild).

После полной пересборки

Ожидается, что в meta CONFIG_HASH = searchConfigHash() и catalog_search_index_ready=Y, иначе поиск может быть отключён до совпадения.

Как работает поиск по запросу (mysql_lexeme_trigram)

Ниже — логическая цепочка; конкретный SQL может меняться.

Шаг 0. Проверки (CatalogSearchService)

  • Индекс готов и конфиг не устарел.
  • Запрос после нормализации не короче 2 символов.

Шаг 1. Кеш числа результатов (опционально)

Для пагинации: на страницах после первой при наличии кеша total тяжёлый COUNT(*) в БД может не выполняться.

Шаг 2. Разбор запроса

  • Нормализация той же схемой, что при индексации.
  • Токены — слова без стоп-слов.
  • Между токенами — AND.

Шаг 3. Для каждого токена — лексемы в словаре

Токен длиной ≥ 3: триграммы → rare-first → пересечение лексем → подтверждение LOCATE по LEXEME_TEXT.

Токен короче 3: точное совпадение или префикс в словаре.

Если по токену лексем нет — ответ пустой.

Шаг 4–6. Товары, счёт, сортировка, страница

Пересечение по токенам на уровне товаров (SQL), максимальные веса по токенам, бонус за имя, порог, ORDER BY + LIMIT/OFFSET.

Шаг 7. total

Отдельный COUNT(*); может быть пропущен при кеше на page>1.

Шаг 8. Карточки

По PRODUCT_ID подгружаются данные каталога для отображения.

Кратко про legacy_token

  • Индекс: myapp_catalog_search_token + документ.
  • Поиск: целой токен или начало (TOKEN = … / LIKE 'q%').
  • При пустом strict — fuzzy для длинных токенов.
  • Подстрока внутри слова — не цель этого режима.

Связь с фильтром каталога

Индекс поиска и индекс фильтра (filter_*) — разные системы. «Свойства в фильтре» в опциях относятся к фильтру; поиск пересобирается по своим настройкам (catalog_search_product_property_codes и т.д.) и searchConfigHash().
